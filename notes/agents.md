## Summary in plain terms

A practical playbook for bringing AI agents into a company responsibly. He recalled the MIT NANDA finding that 95% of enterprise AI initiatives weren't producing a return, largely because companies bought tools without targeting real processes. His fix: treat agents like **new hires**, with a defined job, onboarding, access limits, a named human owner, and measurable results.

## What an agent is

A system that works toward a goal in a loop (act, observe, continue) using tools and context. Five building blocks:

1. **Model:** the language model "brain."
2. **Harness:** software that runs the loop (e.g., Claude Code).
3. **Context:** background information to make decisions.
4. **Tools:** connectors and MCP servers that reach data and systems.
5. **Workstation:** where you run and watch it.

**Assistant vs. agent:** an assistant is back-and-forth for personal productivity; an agent works on its own within set limits, as a unit of work you can place on an org chart.

## Key callouts

- **Start from a process, not a tool.** Find bottlenecks; don't boil the ocean.
- **Map the work first** by talking it through with AI and drawing a flowchart (e.g., Mermaid).
- **Write a charter:** what it does, its boundaries, and how it escalates.
- **Name three owners:** process owner, review lead, system owner. "The agent went rogue" is never acceptable.
- **Protect data:** enterprise accounts only; agents inherit the permissions of the person they work for.
- **Build employee trust:** an AI use policy and openness about what agents can access.
- **Scope cost to the job:** seats vs. token budgets, based on a specific, measurable workflow.

## Example: a shared-inbox agent

A team-inbox agent ("Victoria") triages messages, creates to-dos and updates calendars and files. Its workspace is a folder of text files: **agents.md** (role and boundaries), **skill.md** (instructions and tools), **memory.md** (learned preferences), a schedule and an output location. Keep it portable and build in self-checks that alert a person when unsure.

## How to run a team pilot

1. Pick one recurring job worth improving.
2. Assign the process owner and review lead.
3. Test it.
4. Measure results.
5. Decide to expand, improve or stop.

## Learnings and signals for the team

- **Pick one pilot workflow** (recurring report prep, data pulls, manual spreadsheet work), map it, charter it, and measure before and after.
- **Adopt the three-owner model** for any agent we deploy.
- **Enterprise accounts and inherited permissions only.**
- **Tie agents to measurable ROI** to avoid becoming part of the 95%.
- **Communicate early** about what agents will and won't touch.
